# Runbook: full production reset

Needed only before a second `npm run prod:e2e`: delivering the same 100,000 event ids again would time duplicates that change no published row, and `prod:e2e` refuses to run while production already holds events.

1. Stop deliveries, then disable runs: `npm run setup:prod -- --only worker --runs-enabled false` redeploys with `RUNS_ENABLED=false` (a plain `npm run deploy` turns runs back on when the Google Cloud bootstrap passed). Wait until `GET /api/status` shows `"active_run_id": null` and `GET /api/ops/lake` shows no buffered requests and no pending roll.
2. `uv run --project pipeline peoplelake prod reset --confirm peoplelake` drops every table in the six production datasets and drops and recreates the Iceberg table `peoplelake.raw_events` in Basin Catalog (empty, without a landing cursor). Whether Basin Catalog allows that drop is not verified. If the command reports that it could not, the fallback is a new table name, which is a code change: replace `raw_events` in `pipeline/src/peoplelake/lake/catalog.py`, `src/shared/contracts.ts` and `pipeline/src/peoplelake/contracts.py` (the `LoadResult` table literal) and `pipeline/src/peoplelake/warehouse/loader.py`; run `npm run contracts:gen` and the tests, then `uv run --project pipeline peoplelake lake init --target prod` and `npm run deploy:runner`.
3. Reset the Coordinator ledger with `POST /api/ops/reset` and body `{"confirm": "peoplelake"}` (operator). This starts a new Coordinator generation: run ids carry it, so new ids never collide with retained Workflow instances, and landing rolls are written and listed under `landing/raw_events/g<generation>/`, so the rolls of the old generation are never committed again and nothing in R2 has to be deleted (they stay in the bucket; delete them with `wrangler r2 object delete` later if the space matters, at about 63 MB per full delivery).
4. Re-enable runs with `npm run setup:prod -- --only worker`, then `npm run doctor` and `npm run budget -- --check`.
